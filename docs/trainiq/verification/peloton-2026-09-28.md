**Observed auth flow:** Ran `scripts/debug_peloton_login_403.py` — a
temporary, isolated, one-off diagnostic (per its own docstring, deleted
after this run) that duplicates only `PelotonConnector._login()`'s exact
request shape (`POST https://api.onepeloton.com/auth/login`, header
`peloton-platform: web`, body `{"username_or_email", "password"}`) without
importing or touching any production code, Keychain, or SQLite. Made
exactly one request with real account credentials, entered interactively
via `getpass` (never stored, never logged, never printed).

**Result:**
```
HTTP status: 403
Content-Type: application/json
Response body: {"status": 403, "message": "Access forbidden. Endpoint no longer accepting requests."}
```

This is byte-for-byte the same failure mode Milestone 2's research
documented as occurring between October 2025 and January 2026. **As of
2026-09-28, this breakage is confirmed unchanged, not resolved.**
`PelotonConnector._login()` already handles this exact response correctly
(treats 401/403 as "automated login isn't working right now," routes to
Degraded per ADR-009) — no code change is indicated by this finding, only
a status update on an existing known limitation.

**Manual bearer-token path — tested same day, after the BO supplied a

isolated, one-off diagnostics (`scripts/debug_peloton_manual_bearer.py`,

called `PelotonConnector` or touched its state machine, credentials, or
any persisted state; the token itself was never written to disk or logged,
only held in-process for each request). Findings:

1. `GET /api/me/workouts` (the endpoint `download()` currently calls) →

   show_previous, show_next, next}` at top level — 129 total workouts

## 8. Comparison Against Implementation Assumptions

**Peloton:**
- [x] `GET /api/me/workouts` is still the correct endpoint and response
  shape (BL-008) — **REFUTED.** It 404s. The real endpoint is `GET
  /api/user/{user_id}/workouts`, reached via a prior `GET /api/me` to
  obtain `user_id`. Genuinely paginated (7 pages, 129 workouts) — `download()`
  does not currently loop pages at all.
- [x] Confirm current status of the documented Oct 2025–Jan 2026 auth

**Field-mapping comparison** (`normalize()` vs. the real record shape above):

| `normalize()` reads | Reality |
|---|---|
| `raw.get("duration")` | Field doesn't exist. Derivable: `end_time - start_time` (both present). |
| `raw.get("avg_heart_rate")` / `raw.get("max_heart_rate")` | Don't exist. Only `effort_zones.heart_rate_zone_durations` (seconds per HR zone 1–5) plus `effort_zones.total_effort_points` — no plain average/max bpm anywhere. `effort_zones` itself can be `null` (record 1 above) when a workout has no HR data. |
| `raw.get("avg_power")` | Doesn't exist directly, but `total_work` (joules) / `duration_s` (seconds) = watts is a legitimate derivation, not a fabrication — may differ slightly from Peloton's own UI figure if that excludes rest periods. |
| `raw.get("max_power")` | Not available from this endpoint at all. Must remain `None`, genuinely absent. |
| `raw.get("id")`, `raw.get("start_time")`, `raw.get("distance")`, `raw.get("calories")` | Match as currently assumed. |

## 9. Discrepancies Found

**Two real discrepancies, both in `PelotonConnector`, both now filed as
`aaime921/trainiq#5`:**

1. `download()`'s endpoint (`GET /api/me/workouts`) is wrong — 404s. The
   correct endpoint requires a `user_id` lookup first and is paginated,
   neither of which the current implementation handles.
2. `normalize()`'s field mapping assumes fields (`duration`,
   `avg_heart_rate`, `max_heart_rate`, `avg_power`, `max_power`) that don't
   exist in the real response. Per this project's "never fabricate"
   standard (Eufy `body_fat`/`muscle_mass`, Strava missing `calories`),
   the genuinely-absent ones should map to `None`, not be estimated from
   `effort_zones`/`total_work` — only `avg_power` has a legitimate,
   non-fabricated derivation.

## Addendum (2026-10-09, issue #45): distance-unit finding, and an
## outstanding live-verification gap

**Finding that reopened the distance question:** this file's own full
real record (Section 1, above) carries `distance: 1.2163` with no unit
field anywhere in it — `normalize()` (issue #5) assumed that value was
kilometers, corroborated only by a plausibility check and the unrelated
CSV importer's own `Distance (km)` column, never by a live field. Issue
#45's evidence (the BO's real DB, comparing the same physical rides as
recorded by both the Peloton and Strava connectors via issue #37's dedup
pairs) proved that assumption wrong for this account: Peloton's API
actually returns `distance` in the account's own display-unit setting
(miles here), not always km. `connectors/peloton.py` no longer hard-codes
either unit — see `docs/trainiq/architecture/45-peloton-distance-unit-conversion.md`.

**What was NOT verified here, and why:** that architecture doc's Task 1
calls for a live, one-off diagnostic (same disposable-script pattern as
`scripts/debug_peloton_manual_bearer.py` above) against the real
account's `GET /api/me`, using the BO's manually-supplied bearer token,
to capture the **full** response body and confirm whether a distance-unit
field exists, its real key name, and its real value format — this
file's own prior pass (Section 1) only ever recorded `id` from that
endpoint, not the rest of the body. This Developer routine runs in a
sandboxed environment with no stored Peloton credentials and no network
path to `api.onepeloton.com`, so it could not run that diagnostic itself
— per `docs/trainiq/roles/technical-architect.md`'s "Testing scope
boundaries": live-account testing is BO responsibility, not Dev/QA, the
same constraint this project has applied to every other provider.

**What this means for the shipped fix:** `ACCOUNT_DISTANCE_UNIT_FIELD =
"distance_unit"` in `peloton.py` is still the issue's own suggested
value, not a live-confirmed one — flagged as such in the code itself.
Every live sync today resolves to `None` unless `/api/me` happens to
already carry a field with exactly that name and a recognized value,
in which case future `distance_m` values are correct; otherwise they're
logged and stored as `NULL` (never guessed — AC3), which is the designed,
safe fallback, not a bug. Tracked as `BACKLOG.md` BL-010, left **open**
(not closed-as-verified) until someone with the BO's bearer token runs
Task 1's diagnostic. Unaffected by this gap: the one-off correction script
(`scripts/renormalize_peloton_distance.py`), which takes the unit as an
operator-confirmed `--unit` argument rather than resolving it from
`/api/me` at all.

## Addendum (2026-10-09, issue #47): performance_graph response shape —
## Task 1 resolved, BL-012 closed

**What was verified:** `docs/trainiq/architecture/47-peloton-heart-rate-capture.md`'s
Task 1 called for a live diagnostic against the real account's
`GET /api/workout/{workout_id}/performance_graph`, using the BO's
manually-supplied bearer token, to confirm the response shape, the real
field names for avg/max heart rate and max power, and whether avg cadence
comes "for free" in the same response. The BO ran this directly (read-only)
against a real 45-minute Power Zone ride (2026-10-07, workout id
`819ceb5e…`) and posted the full finding on issue #47.

**Request:** `GET /api/workout/{workout_id}/performance_graph?every_n=60` → 200.

**Confirmed response shape** (top-level keys: `duration`, `metrics`,
`summaries`, `average_summaries`, `effort_zones`, `splits_data`,
`location_data`, among others — not all captured here, only what AC2
needs):

```json
{
  "metrics": [
    {"display_name": "Output", "display_unit": "watts", "max_value": 294, "average_value": 131, "slug": "output"},
    {"display_name": "Cadence", "display_unit": "rpm", "max_value": 128, "average_value": 91, "slug": "cadence"},
    {"display_name": "Resistance", "display_unit": "%", "max_value": 57, "average_value": 34, "slug": "resistance"},
    {"display_name": "Speed", "display_unit": "kph", "max_value": 39.8, "average_value": 28.3, "slug": "speed"},
    {"display_name": "Heart Rate", "display_unit": "bpm", "max_value": 163, "average_value": 135, "slug": "heart_rate", "missing_data_duration": 79}
  ],
  "summaries": [
    {"display_name": "Total Output", "display_unit": "kj", "value": 354, "slug": "total_output"},
    {"display_name": "Distance", "display_unit": "km", "value": 21.21367, "slug": "distance"}
  ]
}
```

**Field mapping for AC2** (implemented in `trainiq/connectors/peloton.py`'s
`_parse_performance_response()`): `avg_hr`/`max_hr` ← the `metrics[]` entry
with `slug == "heart_rate"`'s `average_value`/`max_value` (guarded on
`display_unit == "bpm"`); `max_power` ← the entry with `slug == "output"`'s
`max_value` (guarded on `display_unit == "watts"`). Looked up by `slug`,
never by position — Peloton does not document a stable ordering. A workout
with no HR monitor paired simply has no `"heart_rate"` entry at all, which
`_parse_performance_response()` correctly yields as `None`, never
fabricated.

**Avg cadence:** present in the same response (`metrics[slug="cadence"]`
and `average_summaries[]`) at effectively zero extra parsing cost, but
**not added** as a stored column in this issue's implementation — the
requirements doc's "free or out of scope" framing left this as a judgment
call, and the BO's own unblocking comment on issue #47 did not ask for it
as part of AC2's mapping. Left for a future, dedicated cadence/resistance
issue if ever wanted (see the requirements doc's "Out of scope").

**`hr_total_points` vs. `total_effort_points`:** not re-examined by this
capture (the BO's finding focused on `performance_graph`, not the
list-endpoint `effort_zones` field AC1 already uses) — still an open,
non-blocking curiosity per the architecture doc, not stored either way.

**Shared with issue #57:** this same endpoint and response also carries
`summaries[slug="distance"]` (`value` + `display_unit`), which issue #57
uses for its own distance fix — see
`docs/trainiq/architecture/57-peloton-distance-performance-graph-source.md`.
Both issues' fetches are the same HTTP call
(`PelotonConnector.fetch_workout_performance()`); #47 implemented it first
(this addendum), #57 should extend `_parse_performance_response()` with its
own distance extraction rather than issuing a second call.

**What this closes:** `BACKLOG.md` BL-012, now resolved —
`fetch_workout_performance()`/`_parse_performance_response()` are
implemented against this confirmed shape (no more
`NotImplementedError`), with fixture-based tests from this exact captured
record. `avg_hr`/`max_hr`/`max_power` are no longer hardcoded `None`.
